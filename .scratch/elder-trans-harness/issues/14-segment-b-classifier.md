## 关键设计决定：负例挖矿策略必须绕开 P2 已发现的方法论缺陷

ticket 12 的 P2 探针（教师逐候选判定）测出 82.5% 一致率（未过 90% 门槛），
人工审计 21 条分歧后诊断：根因不是教师判断质量，是**评测方法本身**——
用"候选文本是否落在案例级标注的那一条 evidence 子串里"反推候选级负例，
系统性漏掉了同一 fail 案例里教师没记成 evidence 的其他真实违规词。

**如果段 B 的训练负例直接照抄这个方法（从 fail 案例反推"没命中 evidence
就是负例"），会把这个系统性偏差直接烤进训练数据**——模型会学着对教师
本来就没顾上记录的那类违规视而不见，训出来的东西比不训练更危险（有虚假的
信心）。

**采用的负例来源：只从 `verdict=pass` 的案例里挖负例**。pass 案例是教师对
**整案例**给出的"零违规"判断——这个判断本身没有"只记一条 evidence"的
结构性缺陷（不需要教师去认领"是哪个词违规"，只需要判断"这案例有没有
违规"，这是教师标注环节本来就在做、且做得对的判断）。段 A 规则在 pass
案例上抽出的每一个候选，都是真负例，不需要任何反推。

**实测规模（train 切分，只读统计，未改动任何数据）：**

⚠️ **两种粒度不要混用**（code review 曾发现文档把它们算混）：**合成记录数**
= `synthesize_all()` 返回的条目数（一条记录一个 `synthetic_answer`）；
**候选级正例数** = 段B训练要用的粒度，红线0每条记录展开成 2-4 个候选（注入

edit.py --build` 的 CLI 输出现在两个数都打印，不需要另写脚本换算。

## 门槛（立项时写死，不许训完再定）

沿用 `LITERATURE.md` L1/L2 的判读规则（本票是那两条规则第一次真正生效的场合）：

| 判别项 | 门槛 |
|---|---|
| 候选级红线漏报（真实held-out池，训练不可见） | **≤5%** |
| 候选级红线误报（真实held-out池） | ≤20%（宽松，不对称设计延续） |
| 合成池漏报率 vs 真实池漏报率之差 | **>10pp 判「学到伪影」**，逐条归因后重造，不算通过 |
| 对抗子集（医学正确但原文未给出，≥50条，可直接从合成注入词里抽） | 漏报率 **≤5%**，与总集同门槛，单独报告，不看总分 |
| **绝不报总体准确率**（负例 5415 vs 正例 1332，总准确率会把漏报完全稀释） | 强制要求，代码里体现 |
| **红线0（实体）与红线2（数字）漏报率分开报告，不合并** | L4 新增——数字幻觉在多步推理场景有已知检测短板（虽本项目场景更简单），分开报防止实体类强表现掩盖数字类弱点 |
| **任一 source_case_id 贡献的合成正例数 ≤ 合成正例总数 5%** | L4 新增——防"源文档身份"变成可学捷径（When Hard Negatives Hurt, arXiv:2606.01304），训练前写死，超线判定源文档集中度过高，需扩池不许从同一文档硬多产 |

若未过线：按 ticket 11 记录的既定路径——先查是不是数据不够。候选级正例
**当前是 1,021 条**（审计修复后的最终数字，见文首banner，过 L3 的 ≥1000

若训练后红线0漏报明显差于红线2，第一嫌疑是这个多样性缺口或正例总量已经
太接近下限，不是训练配置，不要重复 ticket 11 的调参弯路。

的 subagent 再看一遍 train 相关代码，找 bug 和方法学错误）

这轮审计比前两轮（自己的 code review、DeepSeek）都深：给 agent 完整的
设计背景（不透露已知 bug 列表），明确要求它既挑代码 bug 也评估方法学
是否站得住，并要求它对每个怀疑都跑脚本实测而不是纯推理。结果：**3 处
contained bug（已修，见下）+ 2 处 SEVERE 级方法学问题（未修，需要决策）
+ 3 处轻微问题（未修，低优先级）**。

### 已修的 3 处 contained bug

1. **`extract_candidates` 对 jargon（set）朴素迭代，进程哈希随机化导致
   `candidate_train.jsonl` 两次生成行序不同**（内容集合相同）——违反项目
   自己的确定性纪律。改成 `sorted(jargon)`。
2. **合成逻辑只检查注入词是否已在 source 里，没检查是否已在原 answer
   里**——如果某个词已经合法出现在真实答案里（比如触发了红线0的身份
   例外条款，案例整体判 pass），再被合成逻辑当"编造注入"标 `violated=
   true`，会在训练集里对同一 `(case, 词)` 组合同时出现 `false`（真实可信
   负例）和 `true`（合成）两条矛盾标签。**实测 train 切分里有 11 条直接
   矛盾**（如 `vt-0215`/阿司匹林、`vt-0656`/泼尼松）。已加 answer 检查，
   修复后核对：candidate_train.jsonl 里矛盾标签数 = **0**。
3. **红线2数字类合成的 `candidate_text` 原来是整句编造短语**（9-13 字，
   如"一般建议每3天复查一次"），**与生产环境段A实际能抽出的候选形状
   （1-5 字的 digit/cn_numeral span）不匹配**——训练正例的候选文本在
   生产环境里永远不会出现，红线2的验收数字测的是一个段A根本不会喂给它
   的分布。改成用同一套正则从编造短语里抽出真实数字/数词 span 当
   `candidate_text`（一条短语可能展开出 1-4 个 span，train/holdout 报告
   口径也同步改了——这是这轮审计自己顺带发现的一个新 bug：A3 改完后
   红线2候选数不再是"每条记录固定1个"，之前的 CLI 统计假设没跟着改）。
   数字 span 本身**不强制** train/holdout 互不相交——数字是极低信息量的
   通用 token（"2""一次"这类），不像药名那样构成"记住这个具体事实"的
   捷径，测试里有专门注释说明为什么这条隔离纪律不套用到数字上。

### 未修的 2 处 SEVERE 方法学问题（需要用户决策）

**问题一：合成正例统一用"答案末尾追加括注"的结构，模型可能只学会认
这个结构，不学真正的原文依据判断。**

实测：用一个只看"答案里有没有出现 `（补充一句：`/`（顺带说一句，`/
`（这类药常见的还有` 这三个模板标记之一"的**退化分类器**（完全不读
source_text，不做任何语义判断），在**对抗子集上跑出漏报率 5%对应的
门槛要求的召回 100%、误报 0%**——ticket 14 自己预注册的 L2 门槛
（"漏报率 ≤5%，单独报告"）会被这个退化分类器直接过线。在真实
train 池上这个退化分类器召回 90.6%、误报 0%（唯一漏掉的是 96 条真实
正例）。核对：0/6,930 条真实答案（train+holdout，正负例都算）含任何
模板标记；100%/1,186 条合成答案以"。）"结尾；合成候选 100% 落在答案
最后 15% 的位置（真实正例候选只有 7.4% 落在这个区间）。

这轮之前已经修过的"词表隔离"（train/holdout 用不重叠的具体药名）堵住
的是一条**窄**泄漏通道（"记住这个具体词"），但**没堵住这条宽通道**
（"记住这个结构"）——`TEMPLATES`（entity）和固定的"（补充一句：X。）"
包装句（numeric）在 `holdout=True`/`False` 两条路径之间是**逐字共享**的。

**推演的最可能训练结果**：模型在合成池/对抗子集上几乎满分，在真实
held-out 池（200条真实正例）上大概率不及格，L1 判读规则里"合成池 vs
真实池漏报率差 >10pp 判学到伪影"这条 tripwire 会触发——也就是说，就算
真去跑 RunPod，大概率跑出来的就是"发现学到伪影，打回重造"，这轮审计
提前把这个归因交上来了。

候选修复方向（未选定，等用户决策）：
  a) 造"模板匹配但内容真实"的**合成负例**——用同样的括注结构，但注入
     的是 source 里**确实有**的实体/数字，让"有没有括注"这个特征本身
     变得没有信息量，逼模型往内容上看；
  b) 编辑位置从"只追加到末尾"改成"插入到答案中段"，打掉位置特征；
  c) train/holdout 用不重叠的模板集合（跟词表隔离同一套纪律，但只堵
     窄通道，不解决"任何括注都可疑"这个更宽的结构特征，单独做效果有限，
     大概率要跟 (a) 一起做才够）。

**问题二：可信池的 drop-uncertain 规则导致候选标签实际上等价于"这条
候选来自哪个答案"，候选级框架从未真正强迫模型在同一答案内部做区分。**

实测：**train 里 0/1,905 个唯一真实答案、holdout 里 0/696 个唯一真实
答案，同时含正例候选和负例候选**——pass 答案的候选全部是负例，fail
答案里保留下来的候选全部是正例（不确定的那部分整条丢弃，这是 ticket 14
本来就刻意的设计，理由仍然成立：单条 evidence 不能证明同一答案里其他
候选是干净的，不能瞎猜负例）。合成正例更是必然全正（整条合成记录就是
为了造正例）。**结果是：`build_candidate_prompt` 里的【候选】字段在
训练时是信息冗余的**——一个只看整个 answer 长什么样（比如是不是带
括注）就能判断的分类器，和一个真正逐候选判断"这个具体词有没有依据"的
分类器，在当前这份训练集/验收集上**产出完全一样的准确率**，没有任何
现有指标能把两者区分开。

直接代价：`candidate_pool.py:52-54` 丢弃的候选（train 352 条、
**holdout 874 条**）恰好就是"违规答案里那些没被判违规的候选"这个层——
也就是部署时最容易出现、且最考验模型"逐候选判断"能力的那类输入（一条
答案里编了一个违规词，但答案里同时还有别的合法具体词，模型能不能只挑
出真正违规的那个，而不是把整条答案的"坏印象"传染给所有候选）。当前
没有任何指标预测得到这种情况下模型会怎么表现。

候选修复方向（未选定，等用户决策，与「问题一」的成本量级相近）：
  抽样教师标注一部分被丢弃的候选（比如 holdout 874 条里抽 100-200
  条，用 ticket 12 P2 的候选级判定 prompt 让教师直接判——**不是从
  单条 evidence 反推**，是真的问教师"这个具体候选有没有依据"），
  用这批新标注在同一批答案里同时造出正负例候选，才能真正测出/训出
  "逐候选判断"这个能力，而不是"整答案分类"。这是实打实的新一轮教师
  标注投入（成本量级参考 ticket 12 P2：120 条候选、3 个 agent、约
  330K tokens/731秒），不是免费的代码改动。

## 问题一+二修复（用户拍板"投入修复问题一+二再往下走"，两处均已实测验证）

### 问题一：结构性负例打掉"括注模板"这条捷径

**修法**：`candidate_pool.build_structural_negatives()`——只对 `verdict=
pass` 的真实案例生效，在答案末尾追加一句**复用同一批括注前缀**
（"（补充一句：""（顺带说一句，""（这类"，跟合成正例用的是同一套模板，
不能另起一套不重叠的措辞，否则退化分类器只需要多认几个新前缀）但**内容
零候选**的安慰语（`STRUCTURAL_NEGATIVE_FILLERS`，train/holdout 各三句，
互不相同）。这样"答案里有没有括注"这个特征在正负例里都会出现，退化分类器
不再能靠它单独判定。`build_adversarial_subset()`/`build_candidate_
training_pool()` 都已接入（结构性负例数量对齐正例总数，约1:1，不是全量
5,000+ 条 pass 候选都装饰——避免正例占比被再腰斩逼近 ticket 09/11 坍缩
区间）。

**验证**（对同一套"只看括注在不在"的退化分类器，在**修复后**重建的对抗
子集上重新跑第三轮审计用过的同一检验）：

| 指标 | 修复前（审计原始实测） | 修复后（本轮重建重新实测） |
|---|---:|---:|
| 对抗子集召回 | 100% | 100%（不变——正例仍带括注） |
| 对抗子集误报率 | 0% | **100%**（新增的结构性负例也带括注，退化分类器现在把它们全部错判成正例） |

误报率从 0% 变成 100%，意味着"括注在不在"这个特征现在对正负例的预测
完全无区分力（两类都是"有括注"，分类器判什么都是同一个答案）——不是
"变难了一点"，是这条捷径被彻底堵死，退化分类器现在等价于恒判正例，比
瞎猜还差。真实模型如果还想在这份对抗子集上拿高分，必须真的读 source_text
判断候选有没有依据。复现命令：`python3 verifier/adversarial_subset.py`
后跑上表同款检验脚本（脚本本身未入库，属于一次性验证，逻辑见本节表格
上方文字）。

### `/code-review` 复审问题一+二的落地代码，发现并修复的真 bug

- **`build_structural_negatives` 的 `max_items` 会超发**：外层
  `if len(out) >= max_items: break` 每条记录只检查一次，但一条记录的
  内层循环可能一次性追加多个候选——卡在刚好差 1 条时，下一条记录如果
  有 N 个候选会整条超发 N-1 条。实测：train 全量 + `max_items=1015`
  时曾返回 1016 条（顶格记录 `vt-1536` 单条就有 26 个可提取候选，理论
  最坏情况能超发到 1040）。已改成硬截断（`out = out[:max_items]`），
  重建后候选级训练集从 7,579 条精确收敛到 **7,578** 条（结构性负例
  1,049→**1,048**，与正例 1,048 精确 1:1，之前是差 1 条的近似值）。

同时顺手清理了三处审计标为"未成活跃 bug 但有漂移风险"的问题（均已加
回归测试）：括注前缀现在从 `synth_minimal_edit.TEMPLATE_PREFIXES` 单
一处定义导入，不再在 `candidate_pool.py`/测试文件里各手抄一份（原来
三份独立副本，改一处忘改另一处不会有任何报错信号）；`"-structneg"`
后缀改成 `candidate_pool.STRUCTURAL_NEGATIVE_SUFFIX` 常量，`train_lora
.py` 统计结构性负例数时改用同一个常量而不是重复字面量；
`build_adversarial_subset` 的 `jargon or load_jargon()` 改成
`jargon if jargon is not None else load_jargon()`——原写法会把调用方
显式传入的空集合 `jargon=set()` 误当成"没传"，静默换成完整生产词表。

另外补了此前缺失的可复现入口：`candidate_pool.sample_uncertain_
candidates()` + `python3 verifier/candidate_pool.py --split <train|
holdout> --sample-uncertain N`——问题二修复用的 250 条不确定候选当初

### 修复过程中自己踩出来的两条，也记在这里

1. **候选形状差点第二次写错。** digit 方向的 `candidate_text` 我写成了「3天」，

   是同一类错误、同一个字段。**它是被一个写错的核查脚本顶出来的**：脚本图省事
